# Alibi Code Review - 2026-05-24 15:09:26

Reviewed against `specs/SPECS.md`, `specs/PROJECT.md`, `specs/STYLES.md`, `README.md`, and the current implementation. This is a review report only; no runtime code, schema, or public API changes were made.

## Findings

### High - Chat logging still needs semantic duration handling

The product contract now distinguishes ongoing-work language from completed-work language. "I started X 30 minutes ago" and "I've been doing X for 30 minutes" should start an open timer backdated by 30 minutes. "I did X for 30 minutes" or "log X for 30 minutes" describes completed work and should clarify when it happened if no start/end anchor is present.

The implementation still converts any draft with only `duration_minutes` into a completed window ending at `new Date()` in `deriveWindow` (`lib/block-draft-utils.ts:107`). `processCompanionMessage` then treats any non-null window as saveable (`app/actions/process-message.ts:1779`) and only asks for clarification when `deriveWindow` returns null (`app/actions/process-message.ts:1780`). The existing unit test explicitly codifies this behavior as expected (`tests/unit/block-draft-utils.test.ts:74`), so the test suite currently protects the bug.

Recommended fix: add semantic handling before the save path. Ongoing duration should call a start-timer path with a backdated `started_at` and no `ended_at`; completed duration should clarify when it happened unless the input supplies a start or end anchor. Narrow or remove the duration-only completed-window fallback from `deriveWindow`, keep the existing `clarificationQuestion` branch that already asks "when did that happen?" (`app/actions/process-message.ts:1409`), and update tests.

### Note - Category inference is acceptable friction reduction

The product contract now allows category inference from input content to reduce logging friction. `resolveCategory` distinguishes extracted and inferred categories (`lib/block-draft-utils.ts:134`), and using the inferred category is acceptable when the evidence is clear. The agent should not claim the user explicitly chose an inferred category, and it should ask only when category evidence is absent or ambiguous enough that saving would create misleading structure.

Recommended fix: keep category inference in the low-friction path, ensure inferred categories remain user-editable after save, and add tests for clear inferred category vs ambiguous category.

### High - "Today" and memory scopes use the server-local day, not the user's timezone

`processCompanionMessage` accepts `timezone` and passes it to the router prompt (`app/actions/process-message.ts:1431`, `app/actions/process-message.ts:959`), but memory range calculation ignores it. `inferMemoryRange` derives "today", "yesterday", week, and month from `startOfLocalDay(now)`, which uses the server process timezone (`lib/memory-context.ts:60`, `lib/memory-context.ts:103`). `getDayRange` has the same server-local behavior (`lib/block-draft-utils.ts:145`).

The contract says default scope is today and user language can expand the context (`specs/SPECS.md:205`), while the README already lists timezone-safe `getDayRange` as pending (`README.md:483`). In production this can fetch the wrong blocks around midnight for users outside the server timezone. The tests currently assert "current server day" rather than a user IANA timezone (`tests/unit/block-draft-utils.test.ts:148`).

Recommended fix: pass the user's IANA timezone into memory range helpers, compute day boundaries for that zone, and update both the helper tests and companion retrieval callers. Avoid fixed 24-hour assumptions around DST transitions.

### Medium - RAG migration conflicts with the portable `app_users` schema path

The portable migration path intentionally references `app_users`, not Supabase Auth (`db/migrations/001_initial_app_schema.sql:1`, `db/migrations/001_initial_app_schema.sql:7`, `db/migrations/001_initial_app_schema.sql:63`). The RAG migration reintroduces direct `auth.users` foreign keys for both `memory_chunks` and `rag_retrieval_logs` (`db/migrations/012_memory_chunks_rag.sql:5`, `db/migrations/012_memory_chunks_rag.sql:31`) and enables Supabase RLS policies (`db/migrations/012_memory_chunks_rag.sql:72`).

That is compatible with the Supabase-hosted path, but it breaks the portability direction described in `PROJECT.md` (`specs/PROJECT.md:66`, `specs/PROJECT.md:68`). It also creates a split ownership model: app tables mostly rely on repository/query ownership checks, while RAG tables rely on Supabase Auth/RLS.

Recommended fix: either mark migration 012 as Supabase-only and add a portable companion migration, or change it to reference `app_users(id)` and enforce ownership consistently through repository queries.

### Medium - RAG fallback can return blocks outside the requested scope

The vector retrieval path honors `sourceTypes`, `match_start`, and `match_end` in `match_memory_chunks` (`db/migrations/012_memory_chunks_rag.sql:122`). If retrieval fails or returns no chunks, the fallback query ignores the requested date range and source types, then returns the most recent completed blocks for the user (`lib/rag/retriever.ts:117`, `lib/rag/retriever.ts:209`).

For a query scoped to yesterday, a date range, or a specific source type, the assistant can receive recent blocks outside the user's requested window. This undermines the evidence contract that memory should retrieve relevant source-backed records, not convenient nearby material (`specs/SPECS.md:23`, `specs/SPECS.md:205`).

Recommended fix: pass the resolved `range` and `sourceTypes` into `fallbackRecentBlocks`. For companion use cases, prefer returning no RAG chunks and falling back to the SQL memory context when scoped fallback cannot be satisfied.

### Medium - Existing block edits do not invalidate the memory-context cache

`lib/memory-context.ts` caches non-today memory contexts for five minutes (`lib/memory-context.ts:324`, `lib/memory-context.ts:368`). `saveBlock` invalidates that cache after new block inserts (`app/actions/timer.ts:1240`) and deletes (`app/actions/timer.ts:1294`), but the existing-block update path revalidates UI paths and returns without calling `invalidateMemoryContextForUser` (`app/actions/timer.ts:1203`, `app/actions/timer.ts:1206`).

As a result, editing a non-today block's notes, category, time, or task can leave companion analysis stale until the cache expires, even though note insight regeneration and RAG reindexing are scheduled for the changed block.

Recommended fix: call `invalidateMemoryContextForUser(user.id)` in the update branch before returning from `saveBlock`.

### Medium - Companion thread loading is still unbounded

`fetchCompanionMessagesForConversation` selects all messages for a conversation and orders ascending without a limit (`app/actions/process-message.ts:540`). `getThreadState` returns that full list to the UI (`app/actions/process-message.ts:833`), and `getCompanionThread` uses it for both the main chat and block-specific threads (`app/actions/process-message.ts:867`).

The prompt path slices recent messages to the last six (`app/actions/process-message.ts:1545`), but the load and response payload remain unbounded. Long-running general chats will get slower and eventually risk large server responses.

Recommended fix: add pagination or a bounded latest-message query for the UI, and only fetch older pages on demand. Keep the small prompt slice, but avoid loading the full thread just to derive it.

### Medium - Some hosted model paths still bypass BYOK resolution

The primary companion flow resolves per-user AI settings (`app/actions/process-message.ts:1491`) and the resolver correctly maps custom providers/models when configured (`lib/ai-settings.ts:684`, `lib/ai-settings.ts:759`). However, note insight extraction imports and uses the hosted `fastModel` directly (`lib/ai-note-insights.ts:3`, `lib/ai-note-insights.ts:70`). The legacy proactive insight writer also imports and uses hosted `companionModel` directly (`app/actions/generate-insight.ts:15`, `app/actions/generate-insight.ts:156`).

This is narrower than the main chat path, and `PROJECT.md` notes the model demotion for note/chat insights (`specs/PROJECT.md:95`). Still, README and SPECS describe BYOK as covering selected-provider chat, notes, time blocks, and memory context disclosures (`README.md:86`, `specs/SPECS.md:268`). A BYOK user could reasonably expect these analysis/generation calls not to use hosted defaults.

Recommended fix: route note insight generation and any still-active proactive writer through `resolveAiModelsForUser`, or document these as server-owned hosted processing paths until migrated. If legacy proactive messages are intentionally retained only for compatibility, mark the action as legacy/internal and avoid invoking it from new flows.

### Medium - Embeddings require server-owned OpenAI credentials but setup docs do not call that out

RAG embeddings are always OpenAI-backed today: `getEmbeddingConfig` only accepts provider `"openai"` (`lib/rag/embedding.ts:16`) and `assertConfigured` throws unless `OPENAI_API_KEY` is set (`lib/rag/embedding.ts:41`). This is separate from BYOK model settings: user provider keys are stored in `user_secret_keys` and resolved by `resolveAiModelsForUser`, not used by `lib/rag/embedding.ts`.

README documents BYOK and hosted OpenRouter defaults (`README.md:84`, `README.md:121`) but does not clearly list `OPENAI_API_KEY` as a separate server-owned embedding requirement. Operators can enable migration 012/backfill and see RAG silently fall back or mark chunks failed without realizing a different provider key is required.

Recommended fix: document `OPENAI_API_KEY`, `ALIBI_EMBEDDING_MODEL`, `ALIBI_EMBEDDING_DIMENSIONS`, and `ALIBI_EMBEDDING_BATCH_SIZE` in setup/configuration docs, explicitly separate server-owned embeddings from user BYOK, and consider surfacing embedding health in admin/debug tooling.

### Low - Verification and style notes

`pnpm lint` is still `"next lint"` (`package.json:10`), which README already says is broken with Next 16 (`README.md:452`). It should not be used as a release gate until replaced with a supported ESLint invocation.

No new UI implementation was reviewed for style conformance in this pass. `specs/STYLES.md` remains the source of truth for component classes and forbids ad hoc visual systems (`specs/STYLES.md:1`, `specs/STYLES.md:3`).
